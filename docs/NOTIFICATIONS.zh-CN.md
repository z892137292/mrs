# Telegram / SMTP 通知

登录 → 消息通知，各渠道独立启用、选事件。Telegram 填 Bot Token 和数字 Chat ID（群组可负号），创建 Bot/向 Bot 发消息等外部账号操作由操作者自行完成。SMTP 填主机、端口、用户名、密码、发件与收件邮箱；465 通常勾选连接即 TLS，587 通常不勾选但强制 STARTTLS。证书验证不关闭。

凭证只保存在 Web 私有 SQLite /data/admin.sqlite（0600，目录0700），不写 GitHub，不通过 GET API 返回；留空凭证保留旧值。禁用渠道会终止其待发项。填写后保存，再点测试通知，查看状态（入队不等于投递）。SMTP 密码可用服务商应用密码，不需要真实微软账号。不要上传 /data、备份或服务凭证。

通知包括时间、脱敏账号、结果/原因、ADMIN_PUBLIC_URL。风险、账号暂停、验证及熔断优先。原上游没有提供可核验的余额时不添加余额猜测。风险未知关联账号时明确是系统/未知，不能虚构某个账号被限制。

事件日志在 rewards 的新 control-data 中最多保留2000项，Web 从持久化游标读取；待发队列最多500项，最多3次尝试，15秒/60秒延迟，不从通知回调再次发通知或触发任务。Web 重启保留发送记录。超过队列容量的普通事件可能丢弃；安全队列也有上限，连续异常不能无界占磁盘。若发送成功后进程崩溃、远端已收到但本地超时，可能有一次重复投递，无法保证第三方协议 exactly-once。

日志只保存通用发送失败原因（网络/TLS/认证/服务拒绝），不保存服务商原始响应、Token URL 或 SMTP 调试对话。外部 Telegram 和实际邮箱投递需要操作者在自己的测试渠道确认；本地协议夹具通过不能替代这种确认。企业微信/钉钉暂未实现，避免影响本轮关键交付。
